# 物理场景与参数说明

完整方法统一为“GAT-PPO 选计算卫星 → 预测接触图路由 → KKT 资源共享”。compute24 与 contact66 是实验场景，不是不同算法。

| 配置 | 用途 |
|---|---|
| `base.yaml` / `ppo.yaml` | 24 星基础物理参数 / 完整学习参数 |
| `experiments/compute24.yaml` | 24 星、较高计算密度，考察热点计算卸载 |
| `experiments/contact66.yaml` | 66 星、80° 倾角、100 Mbit/s，考察接触变化与通信计算协同 |
| `experiments/contact66_balanced.yaml` | 同轨道与业务类型，提高总到达率的压力点 |
| `experiments/low_load.yaml` | 同基础轨道的低负载控制 |
| `experiments/scale24/48/72/96.yaml` | 同轨道族，按每星任务到达和热点比例缩放，冻结跨规模评估 |
| `smoke.yaml` / `rl_smoke.yaml` | 六节点合成网络，功能检查，不用于真实轨道结论 |

参数完整表见 [系统模型](SYSTEM_MODEL_ZH.md)。卫星轨道使用圆轨道 Walker-Delta，当前 ISL 由遮挡、距离、终端度数、跨面纬度及距离排序决定；不保证全部快照连通，也不修改拓扑以偏袒策略。ISL 速率表示分配给该类任务的业务预算，不冒称硬件最大速率。

热点来自混合分布：每星源概率为 `(1-p_h)/S + p_h/H`（热点）或 `(1-p_h)/S`（非热点）。compute24 的 3 颗热点实际承接约 30% 任务；典型每颗 CPU 70 Gcycles/s 时，热点本地负载约 1.37，全局约 .57。因此本地热点可能拥塞而全局仍有余量，卸载有合理动机。此前“3×70 Gcycles/s = 2.1e12”的计算错了一位；正确是 2.1e11。

contact66 的典型全局负载约 .38；热点单星约 .94，具体依 seed 的异构 CPU 而变。`contact66_balanced` 提高到达率至每时隙 18，典型全局约 .62、热点约 1.54，可用于压力敏感性，而不是看到不利结果后替换主场景。低负载即使成功率饱和，也应保留作为控制。

轨道前视不是未来任务先验。策略与路由只能读取 H=16 的未来快照；发送区间不完全覆盖则默认拒绝远程路由。链路变化频率和策略真正经过断链边的频率应分开审计。参考预测、空系统审计不等于实际实现时延。

运行 [服务器审计命令](SERVER_EXPERIMENTS.md) 查看 `calibration.json` 和 `destination_route_exposure.csv`，报告期限下界、全局/热点负载、图连通及路由预测覆盖。参数为工程假设，论文需明确说明，不能仅凭配置文件宣称文献校准或必然优势。
